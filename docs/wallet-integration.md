# 测试钱包接入

来源：用户提供的「钱包系统-复用包.zip」。复用其钱包页面结构、单调三次插值曲线，以及流水驱动余额、幂等入账、先扣后提、失败退款、待入账与服务端规则模型。原包使用 Express + SQLite，本项目使用微信云开发，因此后台适配到现有 orderService，同一云数据库事务内保存订单和账本。

## 当前入口与功能

- 我的 → 收益卡底部「我的钱包」，或收益详情 → 我的钱包。
- 可用测试余额、今日/累计入账、待入账、最近 30 天余额曲线。
- 收支明细、模拟提现记录、金额隐藏、中英文与深色模式。
- 所有操作仅影响测试账本。不存在真实微信转账、充值或资金托管，不调用 requestMerchantTransfer。
- zip 中的 SQLite/JSON 样例账户、流水、余额均未导入。

## 发布到现有测试环境

1. 在微信开发者工具中重新上传部署 `cloudfunctions/orderService`（云端安装依赖），并上传/启用 config.json 中的 wallet-auto-settle 定时触发器（每分钟执行）。不需要新建集合；继续使用 `uniearn_order_state/team-test`。
2. 重新编译小程序，新页面为 `pages/wallet/index`。
3. 如果使用独立网页管理员后台，运行 `npm run admin:prepare` 后再重新部署 adminService，使其携带同一版本的订单引擎及 wallet 模块。
4. 正常测试环境不需要微信商户号、商户私钥或支付环境变量。
5. 如需验证失败路径，可在**测试环境**给 orderService 设置 `WALLET_TEST_WITHDRAW_FAIL=1`，模拟提现后应产生扣款与退回两笔流水，可用余额恢复。验证后删除该变量。客户端不能指定这个失败开关。

## 账本约定

- `state.wallets[accountId]` 持久保存各账户账本，账户身份只取云函数 OPENID 的哈希。
- 金额使用整数分。入账金额只从服务端确认订单的 reward + runnerBonus 计算，客户端不能指定入账或目标账户。
- 入账幂等键：`order-订单ID-创建时间`。提现单由账户ID + operationId 派生，沿用现有请求重试回执，避免并发或断网重试重复扣款。
- 提现先记负流水，再标记模拟成功；失败写一次正向退款流水并置为 rejected。已完成或已退款的单不会再次退款。
- 新安装时，尚未归档的已确认订单逐笔入账；已归档收益按 archived.paid 一次性生成「历史测试收益迁入」。该条计累计收入，不计今日收入。
- 钱包上线后的订单归档前先完成入账，账本保留；不通过修改余额或导入样例补钱。
- 待入账：delivered / disputed。仍在取件或配送中的订单不计为已赚取。争议暂停自动入账。
- 所有订单统一在送达后2小时自动确认入账；用户提前确认则立即入账。保留云同步检查，并增加 wallet-auto-settle 每分钟定时扫描，无需用户保持小程序打开。实际执行受云定时器调度延迟影响。
- 管理员审核扣回按独立负流水入账。如扣回超出可用余额，显示待抵扣金额；后续收入先抵扣，不能通过负余额提现。
- 原包近50条流水/近20条提现的显示上限保留，但后台不删除账本历史。曲线和累计收入计算使用全部账本。
- 历史订单迁入只读现存订单和 archived.paid，不尝试恢复已不可用的逐单记录。

## 测试环境容量

当前项目将团队测试订单集中在一个 CloudBase 文档，并已设置 850KB 事务写入上限。本次沿用该架构，钱包和订单共同受此限制；超限时整体事务失败，不会只扣余额。账本不应通过清空历史来腾空间。真实上线前需要将钱包、流水、提现拆分为独立集合，并接入真实订单支付校验、微信转账结果查询/回调及资金对账后再启用真实提现。测试余额不得直接迁为可提现真实资金。
